# Публичная витрина конвейера разработки: репозиторий + сайт

Дата: 2026-10-11 · Назначение: вход для `/roadmap`

## Цель

Дать работодателю (AI-first команды, hh.ru) проверяемое доказательство того, что я проектирую управляемый процесс разработки с ИИ-агентами, а не просто пользуюсь ими.

Два результата, связанных ссылками друг на друга:
- **публичный репозиторий** с рабочим набором команд конвейера и реальным следом его применения;
- **сайт**, который объясняет конвейер и показывает, как этим конвейером был собран сам сайт.

## Читатели

- **Рекрутер, HR.** Открывает сайт с телефона и тратит 1–2 минуты. Должен понять, что это такое, чем оно отличается от «пишу код с ChatGPT» и куда нажать дальше.
- **Техлид, CTO.** Тратит 10–15 минут. Идёт от схемы к файлам команд и к реальным документам прогона, проверяет, что это не макет.

## Структура репозитория

```
claude-code-harness/
  harness/              # публичный снимок: commands/, agents/, hooks/, CLAUDE.md, settings-фрагмент
  site/                 # Vite + React + TS
  docs/
    specs/              # эта спецификация
    roadmaps/           # дорожная карта проекта
    plans/              # реальные планы, -verify, -review этого проекта (они публичны)
  scripts/              # проверка по списку запрещённых строк, проверка ссылок
  CLAUDE.md             # соглашения ЭТОГО репозитория: команды проверки сайта для /verify
  README.md
  LICENSE
  .github/workflows/    # сборка и публикация сайта
```

## Части

### Часть 1. Публичный снимок конвейера

**Цель:** в `harness/` лежит рабочий очищенный набор ядра, который можно скопировать в `~/.claude` и запустить.

**Источник:** рабочий `~/.claude`, только чтение. **Результат:** `harness/`, `README.md`, `LICENSE`, `scripts/`.

Что сделать:
- Скопировать ядро (решение 3) и фрагмент `settings.json`, который подключает хуки, без личных настроек.
- Почистить по чек-листу: ключи и токены; абсолютные пути и имя пользователя; имена клиентов, проектов и людей; внутренние адреса; ссылки на Linear, трекер времени и прочее окружение; ссылки на lessons (решение 4). Само правило при этом остаётся, убирается только ссылка-обоснование.
- Ссылки внутри ядра на неопубликованные команды и файлы убрать или заменить пояснением.
- Записать в «Факты» дорожной карты краткое описание каждого шага конвейера **по фактическому тексту команд**: что на входе, что на выходе, какая модель, где решение остаётся за человеком, как устроено ревью другой моделью. Сайт берёт описания отсюда, а не из этой спецификации.
- README: что это и для кого; шаги конвейера; установка; что нужно для работы (Claude Code, модели, Codex CLI для ревью другой моделью — по факту команд); какие команды не вошли; ограничения; дата снимка; ссылка на сайт.
- LICENSE (MIT).

**Список запрещённых строк** лежит локально вне git, например в `~/.config/harness-publish/denylist.txt`. Скрипт в `scripts/` читает его по этому пути и проходит по всем файлам репозитория. Ни сам список, ни его строки не попадают ни в один файл репозитория, включая планы: планы этого проекта публичны.

**Критерии приёмки:**
- Скрипт проверки (список запрещённых строк + типовые шаблоны ключей + абсолютные пути домашней папки) находит 0 совпадений по всему репозиторию.
- В `harness/` нет ссылок на файлы, которых нет в `harness/`.
- Нет упоминаний lessons.
- Ручная проверка: `harness/` скопирован в чистое окружение, `/plan` на простой задаче доходит до файла плана без ошибок о недостающих файлах.
- README отвечает на вопросы: что это, как поставить, что нужно, что не вошло, где сайт.

**Зависит от:** —

### Часть 2. Сайт, собранный через конвейер

**Цель:** опубликованный сайт с разделами ниже. Вся сборка оставляет след в `docs/plans/`.

Разделы:
1. **Зачем.** Что теряется при обычной работе с ИИ-помощником: требования, полнота изменений, проверка результата. Один экран.
2. **Конвейер.** Кликабельная схема. Шаг → что делает, вход и выход, где решение за человеком → ссылка на файл команды → фрагмент реального документа из `docs/plans/`.
3. **Устройство.** Команды, субагент проверки с изолированным контекстом, ревью другой моделью, хуки. Почему так: тонкий слой поверх Claude Code, без фреймворков.
4. **Ограничения.** Что проверяется автоматически, а что мной. Модель, проверяющая модель, — известный предел. Цена: тариф и порядок расхода, без точных цифр. Стадии спецификации пока нет. Публичная версия — снимок, а сайт собран рабочей версией.
5. **Подвал.** Автор, контакты, hh, LinkedIn, GitHub.

Раздел «Как собран этот сайт» делается в части 3.

Технически:
- Статическая сборка, `base` под адрес Pages.
- Фрагменты документов подтягиваются из файлов `docs/` при сборке (импорт как текст), а не копируются руками. Так сайт не может разойтись с репозиторием.
- Ссылки на файлы команд — постоянные, на тег или коммит, а не на `main`.
- Шрифты и все ресурсы лежат локально, запросов к сторонним доменам нет.
- Вёрстка работает от ширины 360px, схема доступна с клавиатуры.
- Дизайн самобытный, не шаблон «портфолио разработчика». Можно взять за основу стиль баннера LinkedIn в духе Мёбиуса.
- Публикация через GitHub Actions на каждый push в `main`.
- Команды проверки (typecheck, линтер, сборка, тесты) прописаны в корневом `CLAUDE.md`, чтобы их запускал `/verify`.

**Критерии приёмки:**
- Typecheck, линтер и сборка проходят без ошибок.
- Тест данных схемы: у каждого шага есть описание, вход, выход и путь к файлу команды, и этот файл существует в `harness/`.
- Скрипт проверки ссылок: все внутренние ссылки и ссылки на файлы репозитория живые.
- При загрузке страницы во вкладке Network есть только запросы к своему домену.
- Сайт открывается из РФ без VPN. Ручная проверка с компьютера и с телефона через мобильный интернет.
- На ширине 360px нет горизонтальной прокрутки, схемой можно пользоваться.
- На сайте нет слов «Spec-Driven Development» и «SDD», нет цифр статистики, стадия спецификации не заявлена как часть конвейера.
- Каждое утверждение раздела «Устройство» сверено с «Фактами» из части 1.

**Зависит от:** 1 (описания шагов и пути к файлам).

### Часть 3. Раздел «Как собран этот сайт»

**Цель:** посетитель видит реальный прогон части 2 от постановки задачи до публикации.

- Начало: эта спецификация. Честно указано, что она составлена вручную в диалоге с моделью, потому что отдельной стадии в конвейере пока нет.
- Дальше по шагам: план (критерии приёмки, «Не делаем»), отклонения из «Решений», отчёт субагента проверки, замечания ревью другой моделью (принятые и отклонённые, с причиной), исправления, итог.
- Отдельно: что я проверял руками.
- Везде показываются фрагменты оригинальных файлов со ссылками, а не пересказ.

**Критерии приёмки:**
- Каждый фрагмент берётся из файла при сборке, у каждого есть ссылка на файл.
- На сайте нет ни одного события, которого нет в `docs/plans/`.
- Проверка по списку запрещённых строк по всему репозиторию находит 0 совпадений.
- Раздел описывает прогон части 2. Собственный прогон части 3 только упомянут ссылкой, без рекурсии.

**Зависит от:** 2 (закрыта со статусом PASSED).

- Слова «Spec-Driven Development» и «SDD».

## Беклог

- **Б1. Цифры.** Подсчёт скриптом по артефактам: `docs/plans`, пары `-verify`/`-review`, trailer `Plan:`. Снимок фиксируется с датой. Сначала решить, по каким репозиториям считать.
- **Б2. Проигрывание прогона** по шкале времени из `pipeline-clock.jsonl`.
- **Б3. Стадия спецификации в конвейере.** Когда появится, обновить название и сайт (решение 9). Эта спецификация — ручной прототип такой стадии. Её ход можно взять за основу: вопросы с вариантами-буквами → цель, читатели, решения, части, критерии, «Не делаем», беклог.
- **Б4. Свой домен.**

## Допущения

- `github.io` открывается из РФ без VPN. Это проверяется критерием части 2; если не открывается — переезд хостинга отдельным решением.
- Репозиторий называется `claude-code-harness`, адрес сайта — `<username>.github.io/claude-code-harness/`.
- Codex CLI доступен локально во время сборки.
- Публичный снимок отстаёт от рабочей версии, и это нормально. Дата снимка указана в README и на сайте.

## Риски

- **Сборка сайта — простая задача, прогон может выйти скучным.** Принимаем: честный скучный прогон лучше постановочного.
- **Планы публичны с первого дня, утечка возможна через план.** Защита: проверка по списку запрещённых строк перед каждым push, лучше хуком pre-push.
- **`harness/CLAUDE.md` подгружается Claude Code при работе с файлами в `harness/`.** Пока он совпадает с рабочим глобальным, вреда нет. Если снимок разойдётся с рабочей версией, возможна путаница в правилах.

## Как запускать

1. Подготовить локальный список запрещённых строк.
2. Создать пустой репозиторий `claude-code-harness`, положить эту спецификацию в `docs/specs/`.
3. Запустить `/roadmap` по спецификации → `docs/roadmaps/`.
4. Дальше обычный цикл по частям: `/plan` → `/implement` → `/verify` → `/code-review`.

Ориентир по времени: в первые выходные — часть 1 и план части 2, во вторые — части 2 и 3 и публикация. Часть 4 занимает около часа.
