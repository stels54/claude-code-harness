# claude-code-harness

## Что это и для кого

Набор команд [Claude Code](https://docs.anthropic.com/en/docs/claude-code) для
конвейера разработки **план → реализация → изолированная проверка → ревью
другой моделью**. В [`harness/`](harness/) лежит публичный снимок ядра рабочего
харнеса автора: команды, агент проверки, хуки и `CLAUDE.md` с общими
правилами.

Для кого:
- для разработчиков, работающих с Claude Code, которым нужен управляемый
  процесс вместо разговора с моделью без плана и проверки;
- для тех, кто хочет проверить процесс по файлам: команды лежат в `harness/`,
  а след их применения к этому репозиторию — роадмап, планы, отчёты проверки
  и ревью — в [`docs/`](docs/). Там же лежит спецификация: она написана
  вручную в диалоге с моделью до запуска конвейера, отдельной стадии
  спецификации в конвейере нет.

## Шаги конвейера

Человек запускает `/roadmap` (для больших задач), `/plan`, `/implement`,
`/code-review` и `/manual`. Агент `verifier` запускается сам: из `/implement`
после реализации и из `/code-review` после правок. Типичный вызов:

```
/plan Роадмап docs/roadmaps/<файл>.md, пункт 1      # или /plan <описание задачи>
/implement docs/plans/<план>.md
/code-review docs/plans/<план>.md
/manual docs/plans/<план>.md
```

У `/plan` есть флаг `--no-codex` (пропустить кросс-ревью), у `/code-review` —
необязательный git-диапазон (`abc123..HEAD`); без него ревьюируются
незакоммиченные изменения.

1. **`/roadmap`** — [`harness/commands/roadmap.md`](harness/commands/roadmap.md).
   Большую задачу режет на части-планы с общей памятью: «Факты», «Решения»,
   «Допущения». Результат — файл в `docs/roadmaps/`. Человек отвечает на
   критичные вопросы; если частей три или меньше, команда останавливается и
   предлагает обойтись одним `/plan`.
2. **`/plan`** — [`harness/commands/plan.md`](harness/commands/plan.md).
   Из задачи или пункта роадмапа делает план в `docs/plans/`: атомарные шаги
   с файлом, изменением, референсом, риском и проверкой, критерии приёмки,
   «Не делаем». Код не пишет. Критичные вопросы задаёт до плана и ждёт
   ответа. Затем план ревьюирует Codex; критичное замечание — снова
   остановка до решения человека.
3. **`/implement`** — [`harness/commands/implement.md`](harness/commands/implement.md).
   Выполняет план по шагам с проверкой после каждого. До правок —
   preflight окружения и скептический проход по плану против кода.
   Останавливается и ждёт человека, если план расходится с кодом, шаг упал
   или тест прошёл раньше реализации. В конце запускает агента проверки и
   обновляет роадмап. Коммит предлагает, а не делает.
4. **Агент `verifier`** — [`harness/agents/verifier.md`](harness/agents/verifier.md).
   Изолированная проверка: получает только путь к плану, контекста
   реализации у него нет. Проверяет каждый шаг и критерии приёмки по
   фактическому состоянию репозитория и пишет `docs/plans/<план>-verify.md`
   с итогом PASSED / FAILED / PARTIAL. То, что нельзя проверить в окружении,
   помечается DEFERRED и ждёт подтверждения человека.
5. **`/code-review`** — [`harness/commands/code-review.md`](harness/commands/code-review.md).
   Ревью диффа другой моделью: Codex CLI в режиме только чтения. Каждое
   замечание проверяется по коду; вердикт — «исправлено», «отклонено» или
   STOP, если правка меняет подход, тогда решает человек. Отчёт —
   `docs/plans/<план>-review.md`. Если были правки и у плана уже есть
   отчёт проверки, агент `verifier` запускается повторно.
6. **`/manual`** — [`harness/commands/manual.md`](harness/commands/manual.md).
   По плану и отчёту проверки пишет мануал ручного тестирования в
   `docs/manual/`.

Ревью другой моделью устроено одинаково в `/plan` и `/code-review`: Codex
запускается командой `codex exec --sandbox read-only`, без контекста
обсуждения; до и после фиксируется `git status --short`, чтобы ревьюер ничего
не поменял; каждое замечание проверяется по коду, а не принимается
механически; цикл ревью один.

## Установка

Одноимённые файлы в `~/.claude/commands/`, `~/.claude/agents/` и
`~/.claude/hooks/` будут заменены — в том числе хуки, которые вызывает уже
существующий `settings.json`. Сделайте резервную копию заранее.

Из корня клона репозитория:

```bash
mkdir -p ~/.claude/commands ~/.claude/agents ~/.claude/hooks
cp harness/commands/*.md ~/.claude/commands/
cp harness/agents/verifier.md ~/.claude/agents/
cp harness/hooks/notify.sh harness/hooks/pipeline-clock.sh ~/.claude/hooks/
chmod +x ~/.claude/hooks/notify.sh ~/.claude/hooks/pipeline-clock.sh
[ -e ~/.claude/CLAUDE.md ] || cp harness/CLAUDE.md ~/.claude/CLAUDE.md
[ -e ~/.claude/settings.json ] || cp harness/settings-hooks.json ~/.claude/settings.json
```

- Существующие `~/.claude/CLAUDE.md` и `~/.claude/settings.json` эти команды
  не трогают. Если они уже есть — перенесите вручную разделы из
  [`harness/CLAUDE.md`](harness/CLAUDE.md) (команды ссылаются на
  «Именование документов», «Коммиты», «Вопросы ко мне») и ключ `hooks` из
  [`harness/settings-hooks.json`](harness/settings-hooks.json).
- `pipeline-clock.sh` локально пишет в `~/.claude/pipeline-clock.jsonl`
  время, событие, id сессии, рабочий каталог и до 200 символов первой строки
  запроса или задания субагенту. Если это не нужно — уберите его из `hooks`.
- Хуки вызываются по путям `$HOME/.claude/hooks/…`. При установке в
  отдельный каталог через `CLAUDE_CONFIG_DIR` ставьте ядро без хуков:
  пропустите строки с `hooks` и `settings-hooks.json`.

## Что нужно для работы

- Claude Code.
- Модель: `/plan`, `/implement`, `/roadmap` и агент `verifier` объявляют в
  frontmatter `model: opus`; остальные команды модель не задают.
- [Codex CLI](https://github.com/openai/codex) — для кросс-ревью плана в
  `/plan` и для `/code-review`. Без него эти шаги пропускаются с пометкой ⏭️.
- `git`.
- `jq` — для хука `pipeline-clock.sh`; без него хук ничего не пишет.
- `terminal-notifier` (macOS) или `notify-send` (Linux) — для уведомлений;
  без них хук `notify.sh` молча ничего не делает.
- Chrome-расширение Claude — для браузерной приёмки планов, затрагивающих UI;
  без него такие шаги получают DEFERRED.

## Что не вошло

Не публикуются: команды `from-linear`, `review`, `git-report`, `verify`,
`plan-fix`, `fix-tests` и скилл `lessons`.

## Ограничения

- Публичная версия — снимок. Он обновляется вручную и отстаёт от рабочей
  версии автора.
- Модель проверяет модель: агент проверки и Codex — тоже модели. Проверки,
  невозможные в окружении (браузер без расширения, внешний сервер, ручная
  приёмка), остаются за человеком и помечаются DEFERRED.
- Отдельной стадии спецификации в конвейере нет: постановку задачи
  человек готовит сам.
- Без git-диапазона `/code-review` смотрит `git diff HEAD` и не видит новые
  неотслеживаемые файлы; если изменения состоят только из них, команда
  остановится с «Нечего ревьюить». Перед запуском добавьте их в индекс:
  `git add -- <пути>`.
- Тексты команд — на русском. В целевом проекте команды пишут в
  `docs/plans/`, `docs/roadmaps/` и `docs/manual/`; каталоги создаются при
  первой записи, заранее заводить их не нужно.
- Хуки вызываются по путям `$HOME/.claude/hooks/…` и работают только при
  установке в `~/.claude`.

## Работа с репозиторием

- Исходники сайта — в `site/` (Vite + React + TypeScript, npm).
- Команды проверки сайта и репозитория перечислены в [`CLAUDE.md`](CLAUDE.md).
- Перед первым push поставьте хук: `git config core.hooksPath scripts/hooks`.
  Он запускает `scripts/check-leaks.sh` по пушимым коммитам. Нужен непустой
  список запрещённых строк в `~/.config/harness-publish/denylist.txt` или по
  пути из `HARNESS_DENYLIST`, без него push отменяется с кодом 2.
- Сайт собирается и публикуется GitHub Actions
  (`.github/workflows/pages.yml`) на каждый push в `main`.
