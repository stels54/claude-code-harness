Составь документ ручного тестирования по реализованному плану и его верификации:

$ARGUMENTS

## Что делать

В `$ARGUMENTS` ожидается до двух аргументов через пробел:
1. Путь к файлу плана (`docs/plans/<ГГГГ-ММ-ДД_ЧЧММ>_<имя>.md` или аналог)
2. Путь к файлу верификации (тот же файл с суффиксом `-verify.md`)

Если второй аргумент не передан — найди рядом с планом файл с суффиксом `-verify.md`. Если плана и верификации нет — остановись и спроси пути.

На выходе — **один** новый файл в `docs/manual/`:
- `docs/manual/<ГГГГ-ММ-ДД_ЧЧММ>_<feature-slug>.md` — полная инструкция
  (есть локальный стек: Docker, БД, shell, логи).

`<feature-slug>` выведи из имени файла плана: отбрось его дата-префикс и
`-implementation`/`-plan`. Префикс у мануала — СВОЙ момент создания (он пишется
позже плана), возьми его командой `date +%Y-%m-%d_%H%M`, не копируй из плана.
Если по этому же плану делается парный документ `-only-stand.md` — он наследует
префикс основного мануала. Конвенция — CLAUDE.md, «Именование документов».

## Процесс

### 1. Изучи источники
- Прочитай план **полностью**: контекст, зафиксированные решения, все шаги (цель / файл / изменение / риск / проверка), граф зависимостей, допущения.
- Прочитай верификацию: статусы шагов, какие тесты прогнаны и с каким результатом, раздел «Что требует внимания» (вне-объёмные нюансы и известные ограничения — их обязательно отрази в мануале как «багом не считать»).

### 2. Сверься с фактической реализацией
Не выдумывай поведение — открывай реальные файлы, упомянутые в плане, и выписывай точные факты:
- значения enum/констант, пороги, дефолты;
- точные имена полей в API-ответах и событиях (WS/pub-sub), имена самих событий;
- тексты кнопок и состояний UI (из компонентов), условия их показа/скрытия;
- имена таблиц/колонок, что и куда логируется, содержимое фикстур/сидеров;
- env-переменные и их фоллбэки из конфигов.

### 3. Напиши мануал (`<feature-slug>.md`)
Документ на русском, по шагам **Действие → Ожидание**, с конкретными значениями. Структура:
1. **Назначение фичи** — что и зачем, ключевые ветки поведения.
2. **Чек-лист** (быстрый проход) — пункты с номерами разделов.
3. **Pre-requisites** — окружение, env/config, миграции, проверка состояния БД, очистка, окно логов, сборка фронта.
4. **Happy path** — основные сценарии с проверкой через UI + БД/события.
5. **Дополнительные сценарии / матрица** — покрытие всех веток логики (каждая ветка условия из плана = отдельный кейс).
6. **Edge cases / fail-safe / валидация** — включая способ спровоцировать ошибочные ветки.
7. **Логи / БД / роутинг** — конкретные SQL и grep с ожидаемыми значениями.
8. **Фронтенд-нюансы** — сброс состояния, известные ограничения из верификации.
9. **Автотесты** — команды из плана/верификации с ожидаемым счётом.
10. **Cleanup**.
11. **Приложения** — карта решений/таблица состояний, полезные SQL, что смотреть в WS/Network.

Если раздел неприменим к фиче (нет фронтенда, нет событий, нет БД) — пропусти его, не заполняй ради структуры. Нумерацию оставшихся разделов сохрани сквозной.

### 4. Принципы
- Каждый кейс: **Действие** → **Ожидание** с конкретными значениями (статусы, поля, тексты).
- Покрой **каждую ветку** решения из плана отдельным сценарием — сверяйся с графом зависимостей, чтобы ничего не пропустить.
- Конкретные данные ввода (примеры сообщений/значений) бери из тестов/фикстур проекта, чтобы поведение было воспроизводимым.
- Не предлагай self-healing-обходов; если в верификации зафиксировано вне-объёмное ограничение — описывай его как ожидаемое («багом не считать»).
- Где что запускается (контейнер/host) и на каком языке user-facing строки — бери из правил репо (проектный CLAUDE.md, README), не переноси привычки из других проектов.

## Формат отчёта

После создания файла выведи краткую сводку:

```markdown
Создан мануал в docs/manual/:
- <feature-slug>.md — N разделов, M сценариев

Покрытые ветки: <перечисли ключевые сценарии>
Отражённые ограничения из верификации: <список>
```

Не дублируй содержимое мануала в чат — только сводку и пути.
