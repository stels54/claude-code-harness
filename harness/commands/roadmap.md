Составь роадмап для большой задачи:

$ARGUMENTS

## Что делать

Роадмап — для задачи, которая не влезает ни в один план, ни в секцию
«Вне объёма — следующие планы» одного /plan: частей больше трёх, и
следующие части зависят от того, что выяснится при реализации предыдущих.
Роадмап держит части на уровне целей (шаги остаются планам) и общую
память для всех планов внутри: факты, решения, допущения.

Если аргумент пуст — STOP: «Опиши задачу».

Роадмап — не план: не пиши шаги, файлы, тесты и код. Только части.

## Перед составлением

### Порог
Прочитай релевантный код и набросай декомпозицию. Частей вышло три или
меньше — роадмап не нужен: STOP, скажи «Это один /plan: первая часть +
"Вне объёма — следующие планы"» и файл не создавай.

### Вопросы к задаче
Как в /plan. Противоречия и неоднозначности постановки — сначала списком,
потом вопрос по каждому. Неполнота (умалчиваемые случаи, границы
применимости) — по умолчанию не вопрос: занеси в «Вне объёма» или
«Допущения».

- **Критичные** (меняют состав или порядок частей, выбор подхода) — жди
  ответа, роадмап не пиши. Ответ занеси в «Решения»: вопрос → текст
  выбранного варианта, не букву. Планы и верификатор диалог не видят.
- **Второстепенные** — зафиксируй в «Допущения» и продолжай.

## Требования к частям

- Часть = один /plan = один запуск /implement за одну сессию. Ориентир —
  «Объём плана» из /plan: до 12 product-шагов. Часть заведомо больше — режь.
- Часть самодостаточна: реализуема и проверяема независимо от следующих,
  с наблюдаемым **Результатом** — по нему часть считается закрытой.
- Части — цели, не шаги. Что менять в каких файлах — решит /plan по пункту.
- Порядок — только через **dependsOn**. Зависимость по фактам (часть нельзя
  спланировать, пока в предыдущей не выяснится X) — тоже dependsOn,
  с пометкой, что именно должно выясниться.
- Номера пунктов стабильны: не перенумеровывай и не вставляй новые между
  существующими — на номера ссылаются «Факты» и dependsOn. Новое — либо
  подпунктом `N.x` (см. «Дробление пункта»), либо в конец с dependsOn.
- Роадмап живой: подробно сформулирована только ближайшая часть, остальные —
  черновые цели. Их уточняют при планировании, по накопленным «Фактам», а не
  сейчас. Не расписывай дальние части в деталях — они изменятся.
- Норма — 4–10 частей. Больше десяти — проверь, не склеились ли две задачи;
  если одна — оставь.

## Формат вывода

Сохрани в `docs/roadmaps/<ГГГГ-ММ-ДД_ЧЧММ>_<kebab-case-название>.md`.
Префикс — момент создания, командой `date +%Y-%m-%d_%H%M` (не выдумывай
время). Пример: `docs/roadmaps/2026-09-06_1130_auto-roadmap.md`.
Конвенция — CLAUDE.md, «Именование документов».

В `docs/plans/` роадмап не клади: файл без `-verify`-пары навсегда ломает
автовыбор в /implement.

Статусы и ссылки на планы при создании не заполняй — их проставляют /plan
(📝 + путь) и /implement (✅ / ❌ / ⏸️ по итогу verify). «Факты» при
создании пусты: это память о том, что вскрылось при реализации, а не
пересказ постановки.

### Дробление пункта

Пункт, не влезший в один план при детальном разборе, — штатный случай.
Дробит его /plan (правило — в /plan, «План по пункту роадмапа»). Формат в роадмапе:

- подпункты `N.1`, `N.2`, … с теми же полями; dependsOn между ними — по
  существу (обычно цепочка `N.1` → `N.2` → …), плюс унаследованное от `N`;
- у родителя **Статус** → `разбит: N.1, N.2, …`, **План** → `—`; его
  «Цель» и «Результат» остаются — это критерий закрытия всей группы;
- dependsOn на `N` читается как «все `N.x` ✅»; родитель ✅, когда ✅ все
  подпункты;
- в «Решения» — строка `пункт N разбит на N.1–N.k при планировании:
  <причина>`.

```markdown
# Roadmap: <название>

## Контекст
<одним абзацем: задача целиком, зачем, что считается финишем всего роадмапа>

## Части

Статусы: ⬜ не начат · 📝 план создан · ✅ принят · ❌ verify FAILED/PARTIAL ·
⏸️ DEFERRED, ждёт подтверждения · разбит: N.1, … (см. «Дробление пункта»)

### Пункт 1 — <название>
- **Цель**: 
- **Результат**: <наблюдаемый итог, по которому пункт закрыт>
- **dependsOn**: — | номера пунктов; для зависимости по фактам — что должно выясниться
- **Статус**: ⬜
- **План**: —

### Пункт 2 — <название>
...

## Факты
<append-only, дописывает /implement по итогам verify. Только то, что меняет
следующие пункты. Формат:>
- [ГГГГ-ММ-ДД, пункт N] <что вскрылось> → затрагивает: <номера | —>

## Решения
<вопрос → выбранный вариант. Критичные вопросы при составлении роадмапа,
дробление пунктов, решения по их пересмотру по ходу.>

## Допущения
<второстепенные допущения, не блокировавшие составление>

## Вне объёма
<что намеренно не входит в роадмап целиком>
```

## Формат отчёта

После сохранения — две строки: путь к файлу, число пунктов и какой
планировать первым. Содержимое роадмапа в чат не дублируй.

Не пиши код и шаги. Только части и общая память.
