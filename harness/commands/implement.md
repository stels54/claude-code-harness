Реализуй план по шагам.

$ARGUMENTS

## Что делать

Если в `$ARGUMENTS` передан путь к файлу плана — читай его.
Если аргумент не передан — найди самый свежий файл в `docs/plans/` у которого нет `-verify.md` пары.
Имена планов начинаются с дата-префикса `ГГГГ-ММ-ДД_ЧЧММ_`, поэтому «самый свежий» =
последний в обычной сортировке по имени (`ls docs/plans/`), а не по mtime: mtime
врёт после checkout. Файлы без префикса — legacy, они старше любых префиксных.

Кандидатов без `-verify.md`-пары несколько — STOP: выведи список от старого к
новому и спроси, какой выполнять. Сам не выбирай: старый может быть заброшен,
а новый — зависеть от старого.

## Процесс

### 1. Прочитай план полностью
Перед началом работы прочитай весь план и убедись что понимаешь:
- конечный результат
- зависимости между шагами
- что нельзя трогать

Если что-то неясно — задай вопросы до начала реализации.

### 1а. Preflight окружения
Если все **файлы** шагов плана — документация (docs/**, README, *.md),
preflight пропусти целиком: одна строка «Preflight: ⏭️ (docs-only план)».
Список сервисов/портов и UI-затронутость бери из секции «Окружение» плана,
если она есть; иначе выводи из docker-compose.yml/.env и файлов шагов.

После чтения плана, до первой правки — быстрая проверка (read-only, без side-effects):

1. **Docker**: `docker compose ps` — сервисы из compose-файла текущего репо подняты
   и healthy. Ожидаемые контейнеры и порты бери из docker-compose.yml/.env, не из памяти.
2. **Порты**: порты сервисов из compose свободны либо заняты нашими контейнерами.
3. **Авторизация внешних API**: только если в проекте есть известный дешёвый способ
   (health-endpoint, whoami-запрос). Способа нет — ставь ⏭️, проверку не выдумывай.
4. **Chrome-расширение**: проверяй подключение, только если план затрагивает UI (иначе ⏭️).
5. **Git**: покажи `git status`; грязное дерево — не блокер, просто отметь.

Пункты, неприменимые к проекту, помечай ⏭️. Выведи чек-лист ✅/❌/⏭️.
❌ по пп. 1–3 — STOP: сообщи, что починить, к шагам не приступай.
❌ по п. 4 при UI-плане — предупреди: верификация проставит DEFERRED и коммита
не будет; продолжать без браузера или сначала подключить — решаю я.

### 1б. Челлендж плана

После preflight, до первой правки — один скептический проход по шагам плана
против фактической кодовой базы (read-only). Для каждого шага открой файлы из
полей **Файл** и **Референс** и определи статус:
- **⏭️ ALREADY DONE** — изменение из шага уже внесено;
- **❌ BLOCKED** — шаг опирается на данные/сервисы, которых нет или они пусты
  (таблицы, кэши, фикстуры, внешние API), либо допущения шага о структуре
  файлов/модулей неверны, либо указанного в **Референс** образца не существует;
  в комментарии — что именно не так;
- **✅ CONFIRMED** — иначе.

Выведи таблицу: Step → Статус → Доказательство (файл/строка или вывод команды).
Все шаги ✅ — продолжай без паузы. Есть ⏭️ или ❌ — STOP: к шагам не приступай,
жди моего решения по каждому такому шагу (выполнить как есть / пропустить /
скорректировать план). Согласованные корректировки внеси в файл плана до начала
реализации: правкой шагов и записью в секцию «Решения» — верификатор диалог не видит.

### 2. Выполняй шаги строго по плану
- Строго следуй порядку шагов с учётом `dependsOn`
- Параллельные группы выполняй последовательно — по одному шагу за раз
- Не отклоняйся от плана: нет рефакторинга, нет улучшений "пока тут"
- Если шаг невозможно выполнить как описано — остановись и сообщи, не импровизируй

### 3. После каждого шага
- Выполни проверку из поля **проверка** шага
- Выведи статус: `✅ Step N — <название>`
- Только после успешной проверки переходи к следующему шагу

### 3а. Red-фаза

Тест-шаг — шаг, чья **Проверка** начинается с `red:`. Product-шаг под
red-тестом — шаг, чья **Проверка** — прогон теста из тест-шага.

**Тест-шаг.** Прогони тест. Падает так, как описано после `red:` — это ✅;
п. 4 не применяется. Выведи `✅ Step N — RED` и последние строки вывода.
Тест прошёл сразу — STOP: либо поведение уже реализовано (сверься с 1б), либо
тест ничего не проверяет. К product-шагу не переходи, жди моего решения.

**Тест-файл после red заморожен** до конца product-шага: ни assertion, ни
фикстуры, ни ожидаемые значения не правь. Потребность править тест — признак
ошибки плана, а не реализации.

**Product-шаг под red-тестом.** Попытка = правка product-файлов + один прогон
теста. Лимит — 2 попытки. После второй тест не зелёный — STOP по п. 4, но
варианты не оттуда, а эти. Выведи последний вывод раннера, что менял в каждой
попытке, и один вопрос:
- a) тест требует поведения, которого текущая структура кода не даёт —
  какой шаг плана скорректировать;
- b) тест сформулирован неверно (вход, контракт, точка вызова) — что в нём
  поправить;
- c) продолжать после уточнения: <чего не хватало>.
Рекомендацию дай. Без моего ответа ни один вариант не выполняй — b) это
правка теста, её нельзя делать в одиночку.

### 4. Если шаг упал
- К тест-шагам не применяется; для product-шага под red-тестом варианты — из 3а.
- Остановись
- Опиши что пошло не так
- Предложи варианты: откатить шаг / скорректировать план / пропустить
- Не продолжай без подтверждения

## Запрещено
- Менять логику которую план не затрагивает
- Объединять несколько шагов в один
- Пропускать проверки шагов
- Продолжать после упавшего шага без подтверждения

## По завершении

Выведи итог:

```markdown
## Реализация завершена

**План**: <путь к файлу>
**Шагов выполнено**: N / M

| Step | Название | Статус |
|------|----------|--------|
| 1    | ...      | ✅     |
| 2    | ...      | ✅     |
```

Перед верификацией: если по ходу реализации план корректировался с моего
согласия — внеси корректировки в файл плана (правкой шагов и записью в
«Решения»). Верификатор не видит наш диалог; несогласованное с файлом он
пометит ❌.

Затем запусти верификацию субагентом `verifier`. В задание передай только путь:
«Проверь план <путь к файлу плана>» — без summary реализации, списка изменённых
файлов и своих выводов.

Итог отчёта субагента передай мне дословно (статус и «Что требует внимания»), без собственных комментариев и смягчений.

Единственное, что добавляй после отчёта: при PASSED — предложение коммита
по правилам CLAUDE.md, «Коммиты» (trailer `Plan:`); при DEFERRED — вопрос,
принимаю ли реализацию.

### Синк роадмапа

В «Контексте» плана есть строка `Роадмап: <путь>, пункт <N>` — после
отчёта верификатора обнови роадмап:

- **Статус** пункта: PASSED → ✅; FAILED / PARTIAL → ❌; DEFERRED → ⏸️,
  и → ✅ после моего подтверждения.
- **Факты**: допиши то, что вскрылось по ходу и меняет следующие пункты —
  структура кода не такая, как предполагал роадмап, ограничение окружения,
  отклонение, согласованное со мной. Формат — как в роадмапе, с датой и
  номером пункта; «затрагивает» — по dependsOn. Ничего не вскрылось — не
  дописывай: «Факты» не журнал.
- Остальное в «Частях» не правь: цели следующих пунктов пересматриваются
  при их планировании, через меня.

Правка роадмапа входит в коммит по плану.
