Проверь реализацию по плану:

$ARGUMENTS

## Что делать

`$ARGUMENTS` — путь к файлу плана. Если аргумент пуст или файл не найден — STOP, спроси путь.

## Процесс проверки

### 1. Прочитай план
Выпиши все шаги из плана — id, цель, файл, ожидаемое изменение, проверку.

### 2. Проверь каждый шаг
Для каждого шага:
- Открой указанный файл и убедись что изменение внесено
- Выполни проверку из поля **проверка** если это команда (тест, typecheck, lint)
- Поставь статус: ✅ выполнен / ⚠️ частично / ❌ не выполнен / ⏭️ пропущен / ⏸️ DEFERRED
- Статус ⏸️ DEFERRED — проверка невозможна в текущем окружении (нужен браузер, внешний сервис, ручная приёмка). DEFERRED ≠ пропущен: в комментарии укажи, чего не хватает. Не ставь ✅ шагу, чья проверка фактически не выполнялась.
- Проверка вида `red: … → green после <id>` — проверяй только green: тест-файл
  существует, тест зелёный. Red-фазу по конечному состоянию не проверить —
  за неё ❌ не ставь, это дисциплина /implement.

### 2а. Браузерная приёмка (только для user-facing изменений)
Если план затрагивает UI или видимое поведение в браузере — проверь его через Chrome-расширение на локальном стенде:
- Сценарии бери из поля **проверка** соответствующих шагов плана, не выдумывай свои.
- Фиксируй в отчёте: URL, действие, наблюдаемый результат.
- Расширение не подключено — не имитируй проверку: поставь таким шагам ⏸️ DEFERRED с пометкой «нужен браузер».
- План не затрагивает UI — раздел пропусти целиком, DEFERRED не ставь.

### 3. Запусти общую проверку
Команды бери из проекта (Makefile → scripts в package.json/composer.json → CI-конфиг → README), не выдумывай свои:
- Тесты: релевантный suite в зависимости от затронутых файлов
- Typecheck если TypeScript
- Lint если настроен
- В отчёт вставляй реальный вывод команд (итоговые строки: счётчик тестов, exit-код), а не пересказ. Проверка без вставленного вывода не считается выполненной.

### 4. Проверь критерии приёмки
Критерии — секция «Критерии приёмки» плана; для fix-плана — «Как проверить
фикс». По каждому укажи, чем он подтверждён: вывод команды, состояние
файла, браузерный сценарий. «Шаги N–M выполнены» доказательством не
считается. Проверка невозможна в текущем окружении — ⏸️ DEFERRED с указанием,
чего не хватает. Ни той, ни другой секции нет — строка «Критерии приёмки:
не заданы в плане».

## Формат отчёта

Выведи в консоль и сохрани в `docs/plans/<имя-плана>-verify.md`, где
`<имя-плана>` — имя файла плана целиком, ВМЕСТЕ с его дата-префиксом и без `.md`.
Свой момент создания в имя не подставляй: verify наследует префикс плана, иначе
пара разъезжается в листинге. Пример: план
`2026-07-18_1129_dashboard-1-1-json.md` → `2026-07-18_1129_dashboard-1-1-json-verify.md`.
Конвенция — CLAUDE.md, «Именование документов».

```markdown
# Verify: <название плана>
**Дата**: <дата>
**План**: <путь к файлу плана>

## Результат по шагам

| Step | Цель | Статус | Комментарий |
|------|------|--------|-------------|
| 1    | ...  | ✅     | —           |
| 2    | ...  | ⚠️     | Частично — метод добавлен, тест отсутствует |
| 3    | ...  | ❌     | Файл не изменён |

## Тесты
- [ ] Unit: `<команда>` — <вставка последних строк вывода>
- [ ] Typecheck: `<команда>` — <вставка последних строк вывода>

## Браузерная приёмка
<таблица: шаг → URL → действие → результат, либо строка «неприменимо: изменения не затрагивают UI»>

## Критерии приёмки
| Критерий | Статус | Чем подтверждён |
|----------|--------|-----------------|

## Итог
<PASSED | FAILED | PARTIAL>

Итог PASSED только если все шаги и все критерии приёмки ✅ или явно
DEFERRED. При FAILED/PARTIAL или наличии DEFERRED без моего подтверждения —
коммит не делать и об этом сказать в конце отчёта.

## Что требует внимания
<список проблем если есть, каждая с конкретным файлом и шагом>
```

Если всё ок — скажи "Plan verified. All steps complete." и не добавляй лишнего.
