# Roadmap: Публичная витрина конвейера разработки

## Контекст
Нужно дать работодателю проверяемое доказательство управляемого процесса
разработки с ИИ-агентами: публичный репозиторий `claude-code-harness` с
очищенным ядром команд конвейера (`harness/`) и сайт на GitHub Pages, который
объясняет конвейер и показывает, как этим же конвейером был собран сам сайт.
Постановка — `docs/specs/2026-10-11_public-showcase.md`. Финиш роадмапа:
сайт опубликован, открывается из РФ без VPN, раздел «Как собран этот сайт»
ссылается на реальные документы из `docs/plans/`, проверка по списку
запрещённых строк по всему репозиторию даёт 0 совпадений, выпущен тег v1,
на который ведут постоянные ссылки с сайта.

### Пункт 1 — Публичный снимок ядра и проверка на утечки
- **Цель**: в `harness/` лежит очищенная копия ядра из рабочего `~/.claude`
  (решение 3 спецификации плюс `roadmap`, см. «Решения»): команды, агент
  проверки, хуки, `CLAUDE.md`, фрагмент `settings.json`, подключающий хуки.
  Из текстов убраны ссылки на журнал lessons, на неопубликованные команды и
  файлы, личные пути и всё по чек-листу чистки. В `scripts/` есть проверка по
  локальному списку запрещённых строк, типовым шаблонам ключей и абсолютным
  путям домашней папки; есть `LICENSE` (MIT).
- **Результат**: скрипт проверки даёт 0 совпадений по репозиторию; в
  `harness/` нет ссылок на файлы вне `harness/` и упоминаний lessons;
  `harness/`, скопированный в чистое окружение, доводит `/plan` на простой
  задаче до файла плана без ошибок о недостающих файлах (проверка руками).
- **dependsOn**: —
- **Статус**: ⬜
- **План**: —

### Пункт 2 — README и описание шагов конвейера по тексту команд
- **Цель**: `README.md` отвечает на вопросы «что это и для кого, шаги
  конвейера, установка, что нужно для работы, какие команды не вошли,
  ограничения, дата снимка, где сайт». В «Факты» этого роадмапа записано
  краткое описание каждого шага конвейера по фактическому тексту команд из
  `harness/`: вход, выход, модель, где решение остаётся за человеком, как
  устроено ревью другой моделью. Сайт берёт описания отсюда.
- **Результат**: README есть и покрывает все вопросы из списка; в «Фактах»
  есть запись по каждой команде ядра и по агенту проверки.
- **dependsOn**: 1 — состав и текст `harness/` окончательны, описывать можно
  только опубликованную версию.
- **Статус**: ⬜
- **План**: —

### Пункт 3 — Каркас сайта и публикация на GitHub Pages
- **Цель**: в `site/` проект Vite + React + TypeScript со страницей-заглушкой,
  `base` под адрес Pages, шрифты и ресурсы локально. GitHub Actions собирает и
  публикует сайт на каждый push в `main`. Корневой `CLAUDE.md` репозитория
  содержит команды проверки (typecheck, линтер, сборка, тесты) для `/verify`.
  В `scripts/` есть проверка внутренних ссылок и ссылок на файлы репозитория;
  проверка запрещённых строк запускается перед push.
- **Результат**: заглушка открывается по адресу
  `<username>.github.io/claude-code-harness/`; typecheck, линтер и сборка
  проходят; при загрузке во вкладке Network только запросы к своему домену;
  сайт открывается из РФ без VPN с компьютера и с телефона через мобильный
  интернет (проверка руками).
- **dependsOn**: 1 — проверка на утечки должна существовать до первого push
  публичного репозитория.
- **Статус**: ⬜
- **План**: —

### Пункт 4 — Визуальный стиль и кликабельная схема конвейера
- **Цель**: самобытный дизайн сайта (не шаблон «портфолио разработчика»,
  ориентир — баннер LinkedIn в духе Мёбиуса) и раздел «Конвейер»:
  кликабельная схема, где шаг раскрывается в описание, вход и выход, место
  решения человека, ссылку на файл команды в `harness/` и фрагмент реального
  документа из `docs/plans/`. Фрагменты импортируются из файлов при сборке,
  а не копируются руками. Схема доступна с клавиатуры.
- **Результат**: тест данных схемы проходит: у каждого шага есть описание,
  вход, выход и путь к файлу команды, и файл существует в `harness/`; на
  ширине 360px нет горизонтальной прокрутки и схемой можно пользоваться;
  описания шагов совпадают с «Фактами» пункта 2.
- **dependsOn**: 2 (описания шагов), 3 (каркас и сборка).
- **Статус**: ⬜
- **План**: —

### Пункт 5 — Разделы «Зачем», «Устройство», «Ограничения», подвал

### Пункт 6 — Раздел «Как собран этот сайт»
- **Цель**: посетитель видит реальный прогон пунктов 3–5: спецификация
  (с честной пометкой, что составлена вручную в диалоге с моделью), планы с

## Решения
- Где создавать репозиторий и роадмап → репозиторий `claude-code-harness`
  создан командой `/roadmap` в `~/Projects/Active/` с `git init`;
  спецификация положена в `docs/specs/`, роадмап — в `docs/roadmaps/`.
  Рабочий харнес `development-pipeline` не трогается.
- Входит ли `/roadmap` в публикуемое ядро → входит. Решение 3 спецификации
  расширено: `plan.md` ссылается на правила «План по пункту роадмапа» и
  «Дробление пункта» из `/roadmap`, `/implement` синхронизирует роадмап, а
  сам этот прогон идёт через `/roadmap`, и его след лежит в `docs/roadmaps/`.
  Вырезать эти ветки означало бы опубликовать не те команды, которыми собран
  сайт.
- Часть 4 спецификации (профиль GitHub, hh.ru, LinkedIn, письма) → в «Вне
  объёма»: это ручные шаги без плана, пунктом роадмапа они не являются.
- Части 1 и 2 спецификации разрезаны на пункты 1–2 и 3–5: каждая часть
  заведомо больше одного плана. Пункт 7 выделен из критерия «ссылки на тег
  или коммит»: тег можно ставить только после того, как все документы
  прогона и раздел о сборке легли в репозиторий.
- Описания шагов конвейера записываются в «Факты» (пункт 2) по требованию
  спецификации, хотя обычно «Факты» хранят только вскрывшееся при реализации:
  сайт должен брать описания из одного места, доступного всем планам.

## Допущения
- Хук `pipeline-clock.sh` публикуется вместе с `notify.sh`: под «трекером
  времени» в чек-листе чистки понимается внешний трекер из `git-report`, а не
  локальный jsonl-лог; сам лог не публикуется.
- Шаги «подключи скилл lessons» в `plan.md` и `implement.md` убираются
  целиком как ссылки на неопубликованное, а не только обоснования вида
  `(lessons: дата)`.
- Проверки «в чистом окружении», «из РФ без VPN», «с телефона» — ручные;
  планы фиксируют их как шаги для человека, verify их не выполняет.
- Список запрещённых строк живёт в `~/.config/harness-publish/denylist.txt`
  (на момент создания роадмапа файла нет — его готовит человек до пункта 1);
  скрипт при отсутствии файла завершается ошибкой, а не пропускает проверку.
- Адрес сайта `<username>.github.io/claude-code-harness/`; если github.io не
  откроется из РФ (проверка в пункте 3), переезд хостинга — отдельное
  решение, дописывается сюда.
- `harness/CLAUDE.md` при работе в этом репозитории подхватывается Claude
  Code поверх корневого; пока он совпадает с рабочим глобальным — приемлемо.
- Codex CLI доступен локально во время всего прогона.

## Вне объёма
- Ручные шаги после пункта 7: привести профиль GitHub в порядок и закрепить
  репозиторий; ссылка и строка «О себе» на hh.ru; блок Featured в LinkedIn;
  ссылка в сопроводительных письмах.
- Регистрация, база данных, аналитика, счётчики, формы.
- Цифры статистики (беклог Б1), проигрывание прогона по времени (Б2),
  стадия спецификации в конвейере (Б3), свой домен (Б4).
- Публикация журнала lessons и команд вне ядра (`from-linear`, `review`,
  `git-report`).
- Фрагменты клиентских проектов, английская версия, фото и биография.
- Правки рабочего `~/.claude` ради публикации.
